# Local retained-catalog and captured-surface compatibility

This local fork restores the fixed-width host protocol used by WorldMeshVC. It is separate from the public 1.x retained API; the public API table and version have not changed. New integrations should use the public retained scene API. Existing hosts must resolve and negotiate this private interface explicitly.

## Entry points and contracts

`remixapi_GetRetainedInterface(version, sizeof(remixapi_RetainedInterface), &table)` is a named export of the native runtime and the matching bridge client. `remix_retained.h` defines the unchanged 168-byte record, 80-byte blend block and 40-byte status. A batch contains at most 4096 records. Bridge mesh handles are translated on the server; pointers are never passed between processes.

- `Clear` starts each session with a strictly increasing nonzero epoch. A successful newer Clear resets sticky errors, counters and the catalog. A stale or repeated epoch is rejected asynchronously.
- `BatchUpsert` and `BatchRemove` change the catalog in command order. Mesh destruction removes its dependent private records. Missing materials fail replay closed.
- `CommitFrame` enables the unordered set exactly once for the current runtime frame. The next frame must commit again after camera acquisition and before RTX injection; a missing commit hides the unordered set. Resuming does not require resending unchanged records.
- `DrawOrdered` validates the full ID group before submission and applies its order through the scene's existing decal-order counter. Ordered records must be explicitly drawn each frame. An invalid group cannot leave a visible successful prefix.
- `GetStatus` drains CPU command processing before returning the catalog status. It does not wait for GPU completion or read GPU buffers. Hosts should query during initialization, reset or diagnostics rather than each frame.

The adapter owns descriptions and dependency indices, while the new `RetainedScene` owns persistent render instances, shared geometry and GPU instancing. Ordinary unchanged commits perform no per-record rebuild or draw resubmission. A mesh/material event touches its indexed users; scene resets, texture-cache resets, mod changes and relevant translation-option changes rebuild affected descriptions. There is no old retained backend, quality reduction or CPU expansion of GPU instances.

## Version 3 visibility and transform updates

Request version 3 first and fall back to 2 when negotiation fails. Both versions use the same record and function-table layout; the returned table echoes the requested version. Each version has its own permanently versioned `BatchUpsert` wrapper: obtaining a v3 table never enables v3 flags through a previously obtained v2 table.

`REMIXAPI_RETAINED_HIDDEN` (2) keeps an unordered description resident while hiding all its render children. Combining it with `ORDERED` is invalid. A hidden record still contributes to `instanceCount`, but does not contribute to the unordered `submittedCount`. A host must commit each frame, including when every resident record is hidden. Missing commits hide the current render set without changing host visibility intent; a later commit restores only records whose HIDDEN flag is clear. Mesh/material invalidations and scene-cache resets retain this intent. Mesh destruction and Clear still remove descriptions.

Transform/HIDDEN-only upserts update existing child transforms and visibility without re-resolving surface materials or replacements. Replacement prims keep their authored relative transforms and attached lights follow the parent transform. Changes to mesh, blend, categories, cull mode, wetness or picking identity continue through full preparation and replacement resolution.

A bridge v3 request requires `GetGameValue("vc.client.retainedVisibilityVersion") == "3"`. The client rewrites to a bridge-only key; the matching server must obtain a v3 runtime table and query the runtime-only key before returning the capability. The v3 table request also waits for runtime acknowledgement. Old endpoints cannot advertise this support merely by forwarding a native capability query. The two new wire commands are appended; all v2 command numbers remain unchanged.

## Visibility-only batches

A V3 host can send visibility changes for existing unordered instances using
`remixapi_GetRetainedVisibilityInterface(1, sizeof(table), &table)`. In a bridged
process, require `GetGameValue("vc.client.retainedVisibilityDeltaVersion")` to
return the two bytes `1\0`. The matching server checks the native extension
table and the native capability. Older endpoints keep the V3 full-upsert path.

`BatchSetVisibility(epoch, visible, count, ids)` accepts 1–4096 nonzero 64-bit
IDs and one shared visibility value of 0 or 1. A repeated ID applies the same
intent. The renderer validates every ID before changing any record. An unknown
or ordered ID latches the retained error and suspends replay until a newer
`Clear`. A successful call enqueues the command on the retained submission
stream. Use existing status and epoch recovery for asynchronous errors.

Send new or changed descriptions through `BatchUpsert`. Use visibility-only
batches for IDs whose geometry, material, transform and tags are unchanged.
Keep those sets disjoint and enqueue them before `CommitFrame`. Each such ID
uses 8 payload bytes, compared with 168 bytes for a complete record. Both
routes use the same visibility policy for scene children and replacement
effects. The graphics presets do not control the protocol.

## Original-surface fusion

`rtx.scene.aggregateLegacyRetainedGeometry` defaults to `True`. The developer
menu exposes it as **API Retained: Combine Compatible Legacy Surfaces**.
Turning it off disables both within-parent fusion and cross-parent world batches.
The next retained scene refresh rebuilds the published geometry from its source
descriptions and restores each child's visibility. Ordered groups still replay
at their explicit draw positions. Scheduled USD captures request original mesh
identities before the retained scene is refreshed.

For one unordered parent, dirty preparation may physically concatenate compatible original API surfaces into one vertex/index buffer and one render child. Original per-surface identities and asset dependencies remain in the API mesh; a matched enhanced mesh replacement always resolves separately. Eligibility requires identical opaque material/alpha/layout/cull state, one parent transform/visibility lifetime, no skinning or special surface service, and equal current hash-specific wetness rules. Device-local or unsupported layouts retain their original surfaces.

The fused rendering view is reused until a description, asset, translation option or applicable rule changes. A capture trigger (including pending triggers), picking/highlighting requests or an active picking image restores original surfaces before this frame's upload. Wetness rule changes reclassify candidates in the same frame. Ordered draws remain at their existing call positions.

`[RetainedBatch]` reports source surfaces, actual render children and cumulative fused builds every 240 frames. These counts must demonstrate an actual surface reduction before attributing a performance result to fusion. A bounded per-Compat geometry cache shares immutable fused buffers across placements of the same source ranges (64 MiB / 256 entries), while parent transform/material/visibility remain separate. Its key retains source buffers and compares their full layout/ranges after hashing. Eviction releases only cache ownership; live children retain their geometry. Cache hits/creates/bytes are included in the log. This same-parent cache is separate from the cross-record world-cell view below.

## Cross-record static world-cell batches

The compatibility adapter can physically pack eligible surfaces from different unordered records into shared vertex/index buffers and fewer render children. It groups by 64-unit cells of the resolved part's world translation, original game-texture hash, current wetness rule and compatible final material/surface/cull state. Material comparison covers every opaque constant and texture resource, sampler choice, legacy alpha and texture operations, texture transform, category and vertex-attribute presence. This is an internal rendering view; it adds no API function and does not change the public C table or private v2/v3 record layouts.

The original-surface helper, pure enhanced-part resolver and world-cell helper share the same authored-emission rule: disabled emission or an authored intensity exactly equal to zero is eligible. An enabled flag with zero intensity does not emit; the material shader skips its emissive texture operations and window-emission branch. Enabled nonzero intensity, including negative, infinite or NaN values, remains on the canonical path. The check does not use a tolerance, the global emissive scale, a black color constant or the current lamp schedule. All authored enable/intensity/color/texture fields remain unchanged. A later material or legacy-default change invalidates the source descriptions and re-evaluates eligibility.

World grouping and source-cache comparison require equal original texture hashes in addition to the full resolved texture-resource comparison. The runtime resolves an original texture name by that hash and obtains a replacement name from the resolved albedo texture's managed resource. Keeping both identities avoids grouping sources that would classify differently under window texture rules. Actual nonzero emissive windows remain canonical; this change does not merge their per-instance window seeds, island identities or cached emissive-triangle history.

Each canonical render child is expanded through the existing mesh-replacement rules before grouping. Pure opaque enhanced parts retain the resolver's running material/categories and `parent * authoredRelative` transform; original API identities, canonical descriptions and asset dependencies remain owned by their source records. Empty replacements continue to suppress the original. A child participates only when all its expanded parts are supported and can be assigned to cross-record batches. Lights, graphs, particles, portals, instancers, skinning, clipping/texgen, blending/alpha testing and unsupported or non-host-readable layouts remain on the canonical path. Negative-determinant transforms are excluded. Ordered records keep their call positions. A record that changes transform after insertion permanently leaves this optional view for that record's lifetime.

The adapter validates complete, unique part ownership and builds every required rendering view before hiding any canonical child. The scene-thread transaction completes before upload. Stable already-visible views are not temporarily hidden and shown again. A required scene-view rebuild may set its desired visibility during the scene-thread staging transaction; every operation completes before upload, and a failed prefix destroys optional views and restores canonical children. A failed preparation, allocation, coverage check or retained build restores the canonical sources. Capture triggers, including pending triggers, and picking/highlighting requests restore canonical identity-bearing children before upload. Asset/translation invalidations re-resolve the canonical source descriptions; wetness rule changes restore the current canonical state in the same frame. Optional readmission to world batches can follow later. Hidden intent and missing-commit behavior apply to both views, and a later commit cannot reveal a host-hidden record.

Fixed membership, transforms and state reuse the packed vertex buffer. A visibility-only update selects the visible members' stored index ranges without decoding or repacking vertices. A nonempty set differing from the last built nonempty mask creates a new active index buffer. All-hidden batches retain the last nonempty index buffer and rendering state, remain hidden and do not advance the geometry revision. Revealing exactly that saved mask reuses its index buffer/state and geometry revision; a different nonempty mask still builds new topology. An initially all-hidden batch has no reusable nonempty topology and builds its first index buffer on reveal. Hidden batches never draw their retained nonempty indices. A resident retained view only needs its visibility restored. With release policy 0, hiding invalidates view readiness and reveal rebuilds that scene view in the same frame using the retained index buffer, even when its geometry revision is unchanged. Visibility policies may still cause BLAS work; index reuse does not guarantee zero GPU visibility cost. The generic backend requires a nonzero immutable vertex identity plus exact resource/range/layout and vertex-hash equality before preserving vertex/history buffers. A changed nonempty index topology still requests a full BLAS build, updates topology-dependent state and invalidates opacity micromaps; this is not a BLAS refit or a promise of unchanged GPU work. A stable frame with no dirty event skips batch preparation.

Structural reconciliation is separate from visibility updates. A successful full preparation records an exact membership generation and an index from canonical child IDs to every accepted batch containing their parts. Global state invalidation forbids reusing an obsolete resolved source. Local canonical changes can instead detach their old batch membership, as described below. Visibility alone does not re-snapshot canonical descriptions, resolve replacements, regroup materials or redo capacity selection. Unknown nonzero child IDs remain canonical and cannot create new membership through the fast path; admission of new geometry requires a full preparation.

For an unchanged membership generation, only changed members' affected batches stage a new visibility mask and, when needed, a new active index buffer. Immutable packed vertices, source ownership and member ranges remain unchanged. All parts of a child, including parts assigned to multiple batches, are staged together on the same CS/scene-thread transaction before upload. A failed preparation or a failure after publishing a prefix destroys the optional views and restores all canonical children; partial ownership is not left rendering. This transaction does not imply GPU execution has completed. All-hidden batches publish hidden state rather than drawing the last nonempty topology. A missing host commit hides the views but preserves membership; the next valid commit republishes all cached views even when their triangle masks did not change. Lost publication readiness cannot be recovered by a visibility-only update.

Local changes or removals detach canonical children from existing batches before their committed replacements can render. The adapter captures the old owned child IDs and combines forced detachment with final visibility changes and missing-commit presentation in one scene-thread index transaction. Detachment wins over a simultaneous show. Every part of each old child is removed across all affected batches; only after successful batch publication does the adapter release the corresponding ownership and show the canonical children from the latest successfully published source. Packed vertices, batch handles, other members and their ordering remain stable. Old source ranges stay quarantined in immutable storage until a later full preparation; forgetting their membership locations prevents a reused canonical handle or republish-all from reviving the old mesh.

Optional structural readmission is pending-driven and uses a one-second steady-clock interval; the first pending admission may run immediately. The timer alone does not scan or rebuild the catalog. Canonical geometry and enhanced replacements from the latest successfully published source render while admission waits. A full description waiting for the next host commit remains separate from that published source/record. Global refresh re-resolves the published source, while indexed API asset changes refresh only their actual published users. Same-description fast transform and visibility changes retain their existing timing, without promoting a pending full description. Asset dependency and destruction handling cover both pending and published identities.

Global asset, texture, translation-option, applicable wetness-rule or identity-tool changes require current canonical resolution before upload; this work is not deferred with optional batch admission. A missing commit still hides every presentation and requires republishing on resume. Staging, publication or partial-prefix failure restores canonical rendering and invalidates optional-view readiness, preserving the original capture/picking fallback.

Fixed world chunks preserve the packed vertices, physical member slots, geometry identity and batch handle of unchanged sources across optional admissions. Before retaining ownership, the planner verifies every part of a canonical child against its saved source and its exact still-owned physical index location, and excludes children pending detachment. If any part changes or disappears, that child's old parts retire together across chunks. Published ownership includes only active members; immutable source-range metadata is not authority to resurrect a retired member. Reusing the same canonical child ID for new geometry cannot reactivate its old physical slots.

Only complete uncovered children enter the new-delta grouping and capacity plan. Existing valid chunks stay in place instead of being regrouped when unrelated placements stream in or out; new sources never append to their physical slots. A change in member visibility still selects active indices, with the same hidden/reveal index reuse and canonical failure behavior described above. Retired physical slots remain holes in immutable storage and continue to consume their full byte, chunk and physical-part budget until that chunk is released; fully dead chunks can be released as a whole. Keeping old chunks, admitting new chunks and publishing active ownership remain one staged transaction; no canonical child is suppressed for only some of its parts. Global invalidation still clears and re-resolves the optional cache.

Resolved source-part vectors are borrowed from their owning compatibility entry only during synchronous world-batch preparation, rather than copied into every input snapshot. Cached source descriptions, physical ranges and physical member identities live in shared immutable chunk storage. Cached rendering plans and fast visibility outputs carry no ownership-member list; only full preparation builds a separate active ownership list from that storage. Callers update ownership only from full output or successful permanent detachment. These changes retain strong source-resource lifetimes and the same staged ownership, complete-child proof, invalidation and canonical fallback rules. The full topology index vector was already shared before this change and is not a newly removed copy. This is metadata reuse; it does not eliminate required new-delta vertex packing, changed-mask index generation or backend BLAS work.

The CPU complete-input proof uses a compressed input/part/bucket incidence index and a rejection queue instead of rebuilding coverage arrays and rescanning every bucket until no input changes. Removing an incomplete child propagates through dependent bucket coverage until the same complete-child fixed point is reached. Input/part validity, cross-input batching eligibility, deterministic budget selection and canonical fallback remain unchanged. The queue changes this CPU proof implementation only; source/material grouping, fixed chunks, physical-slot ownership, visibility, GPU buffers and BLAS work retain their existing rules. Existing R8 successful-transaction phase counters remain the telemetry contract; no additional phase fields are introduced.

Diagnostic tracing reports each successful helper full preparation as `[WorldBatchWork]` with seven clock boundaries and six CPU phases: `fullFixedProofMs`, `fullCandidatesAndGroupingMs`, `fullCoverageBudgetMs`, `fullFixedStageMs`, `fullNewPackMs` and `fullMembershipIndexAndCleanupMs`. The final phase includes membership-index work, publication bookkeeping and destruction of all temporary state and swapped-out old cache. `success=helperPrepare` means the helper published its cache/output; it does not mean later compatibility publication or GPU completion succeeded. Failed helper preparations produce no success timing event. `totalMs` ends before helper log formatting and excludes earlier validation/entry overhead. The noexcept diagnostic destructor catches logging failures without changing a successful return.

`[WorldBatchPublish] success=compatPublish` records each successful compatibility full publication with `snapshotMs`, `prepareMs` and `publishMs`, plus input/ownership/visible-subset counts. Its `frame` and `prepareAttempt` pair with the helper event from the same transaction. These frames come from `DxvkDevice::getCurrentFrameId`; benchmark `hud_frame_id` comes from the independently incremented `HudFrameTimeItem::m_sourceFrameId`. Equality of those frame domains has not been proved and must not be used as a direct join. Logger wall time and formal elapsed time permit approximate temporal context only, preserving queueing, asynchronous execution and clock uncertainty; proximity does not prove cause. Helper log formatting lies inside outer `prepareMs`, while the helper total ends before formatting. A positive residual is expected to include diagnostic overhead, not automatically missing algorithm time. Publication log formatting is outside its own recorded phases.

Normal `[Perf]` intervals append fixed `stageSamples`, `blasBuildMsPerSampledFrame`, `tlasBuildMsPerSampledFrame` and `sceneSetupMsPerSampledFrame` fields under `acceleration GPU`. They read existing stage sums and divide by all sampled ray-traced frames in that interval, rather than per-label presence or all presents. Missing labels or zero samples report `n/a`, not zero. The fields are independent of the existing top-five stage display and require no new GPU queries or sampling changes. These are global acceleration stages, with no world-batch/index-only attribution. Diagnostics add clock, formatting and logging cost; they change no ABI, setting, rendering or admission rule and are not a performance optimization.

World-batch accounting is bounded at 128 MiB for packed vertex buffers, stored CPU topology and the maximum active index-buffer size, with at most 256 batches and 65536 physical parts, including retired holes. It is not a limit on all runtime allocations; canonical source resources and temporary old/new allocations during transactional replacement can coexist. The 64 MiB same-parent cache above has its own budget. Existing valid chunks first reserve their full accounted cost, including retired holes. Before packing new vertices or allocating new buffers, the planner applies complete-child capacity preflight to the new delta; rejected children remain entirely canonical without reshuffling stable chunks. Over-budget components keep all their canonical children while independent admitted components remain batched; zero admitted components is a valid all-canonical result. This preserves complete replacement ownership and avoids discarding the entire world view merely because one component exceeds capacity. Actual allocation, mapping, packing or publication failure still uses the full transaction fallback. Limits or unsupported input do not reduce geometry or quality.

`[WorldBatch]` reports input/owned canonical children, visible source parts and visible batches, cumulative builds/failures, vertex builds, index builds, vertex reuse and accounted bytes. Compare `visibleParts` with `visibleBatches` to verify actual render-surface reduction; inspect `vertexReuses` and index-only activity to distinguish geometry reuse from repeated packing. Budget rejection counters are separate from allocation/packing/plan failures. `snapshotMs`, `prepareMs` and `publishMs` sample CPU work for the first 16 full/fast calls and then at 240-frame gaps; they do not measure GPU completion. `[WorldBatch] mode=full` reports structural reconciliation, while `[WorldBatchFast]` separately reports visibility changes, affected plans, membership-preserving calls and failures. Full and fast event timings must not be pooled as a per-frame average. Each successful full/fast transaction contributes to separate cumulative CPU counts, phase totals and lifetime maxima. Both sparse streams carry `fullCpuCalls`, `fullSnapshotMsTotal`, `fullPrepareMsTotal`, `fullPublishMsTotal`, `fullSnapshotMsMax`, `fullPrepareMsMax` and `fullPublishMsMax`, with the corresponding `fast`-prefixed fields. Matching-bound count/total deltas permit interval means per successful transaction even when no full event happened exactly at a logging boundary. A cumulative maximum is a lifetime observation since clear, not an interval maximum obtained by subtraction; missing older-run fields are unavailable. Failed transactions remain in failure/resource counters but are excluded from these phase totals. Four clock observations per successful transaction delimit snapshot/prepare/publish; prior global refresh, logging formatting and CPU-stat updates are outside that timing. Full and fast logs have independent 240-frame sparse cadences, so fast events cannot consume the full-log sampling opportunity. Shared cumulative geometry counters sampled on fast events may include intervening full preparations. The legacy `indexBuildAttempts` and `indexBuilds` count logical mask-transition processing, including all-hidden transitions that allocate no buffer; they must not be interpreted as GPU allocation counts. `indexAllocationAttempts`, `indexAllocations`, `indexBytesUploaded` and `indexTrianglesUploaded` report actual index-buffer resource/write work, including work performed by a later-failed staged transaction. These are not Vulkan device-memory allocation-call counts. `revealReuse` and `allHiddenNoAllocation` count successful helper cache transactions; scene publication failure remains a separate failure. Failure diagnostics are bounded and cannot throw. Fixed-chunk/delta admission statistics are gauges from the last full preparation, including retained bytes, resident/active physical parts and admitted delta children; they are not instantaneous membership counts between admissions. Active parts mean still-attached canonical members, including currently invisible members; they are not a visible-geometry count. Resident parts also include permanently detached holes. `vertexAllocationAttempts`, `vertexAllocations` and `vertexBytesUploaded` count actual buffer-resource/write work, including work from later-aborted staging, while legacy `vertexBuilds` remains a committed-cache count. Resource creation does not measure vkAllocateMemory calls. These counters do not establish an FPS improvement or visual equivalence.

Hidden runtime instances skip wetness-rule, material and texture-name classification queries. Window classification is cleared before that early skip, including the final window-disable pass. Revealed instances are classified after retained/view-model updates and before the same frame's merge and surface upload. `[SurfaceClassify]` reports classified/hidden input totals and average/maximum loop CPU time for each logged interval; the earlier window rule/memo reset is outside this timer. These values reset after logging and are not lifetime cumulative counters or GPU timings.

## Captured legacy surfaces

`remix_legacy_surface.h` and `remix_legacy_surface_v2.h` attach per-surface original identities. These must come from the current session's observed game draws. Do not fabricate identities for real game content. The geometry's API storage/cache identity remains distinct from its original replacement/capture identity.

The runtime verifies the configured hash-rule fingerprint, nonzero draw/geometry keys, the draw = geometry XOR material relation, surface counts and extension exclusivity. Material zero is a valid untextured identity. V2 also carries the original absence of normals; a missing normal stays missing instead of being replaced with an invented normal buffer. Unknown flags, reserved bits, invalid strides and malformed payload lengths are rejected.

V2 support is an end-to-end handshake. A bridge host requires `GetGameValue("vc.client.legacyVertexAttributesVersion") == "2"`; the client rewrites the query to a bridge key and the server rewrites it to the runtime key. The native runtime advertises only `vc.api.legacyVertexAttributesVersion`. Intermediate keys are not independently advertised. A size probe returns 2 including the terminator; a one-byte buffer remains untouched. Do not infer support just from a header or synthesize a capability response.

Original texture categories include zero-texture rules, normal smoothing, decal variants, baked-lighting/opacity exclusions and player/particle categories. Material replacements resolve by the original game texture key; capture keeps the observed material key. Mesh replacements resolve by the original draw key through the current frontend resolver.

## Game texture material binding

The matching bridge implements `dxvk_GetTextureHash` for its D3D9 texture objects. The native frontend drains pending CPU commands, obtains the existing DXVK image hash and registers the actual texture view with the scene texture table. It neither hashes pixels on the CPU nor reads pixels back from the GPU. `CreateMaterial` accepts `game:0x<16-digit-hash>` and confirms that an opaque material resolved a valid albedo texture before returning success. Failure returns a null handle.

`vc.api.gameTextureMaterialVersion`, `vc.api.gameSurfaceVersion`, `vc.api.legacySurfaceVersion`, `vc.api.zeroLegacyMaterialVersion` and `vc.api.retainedOrderedVersion` return `"1"`. `vc.api.legacySurfaceRule` returns the active rule fingerprint in hexadecimal.

The provided old source does not register `rtx.vcApi.textureHashMode`; its current texture lookup always uses `DxvkImage::getHash()`, CPU command synchronization and texture-table registration. That behavior is preserved directly here. The obsolete configuration key is not a capability signal. Old compact-vertex/index experimental storage toggles are not reintroduced.

## GPU-instancing bridge payload

The existing `InstanceInfoGpuInstancingEXT` serializer is now connected to `DrawInstance` in both bridge endpoints. One payload contains the 12-byte serialization header followed by contiguous 48-byte transforms. The bridge accepts up to 65536 transforms (3 MiB); nonzero count with null data, a duplicate extension, an over-limit count, mismatched stype and any nonexact payload length are rejected. The client sends one draw command, not one command per transform. Count zero retains the native public API's ordinary single-instance fallback semantics.
